# Detailed requirements: v1.0 status and v1.1 backlog

This file records the 65-item product requirement audit from 2026-11-24. It is deliberately separate from the course compliance matrix in [`course-requirements.md`](course-requirements.md): the course requirements in `Final project description.md` are substantially met, while this list contains the extra product requirements that we consciously did not all implement in v1.0.

Use this file as the report appendix or as the input to the v1.1 plan. Do not merge the two documents: the course matrix answers what the course asks for; this file answers what the larger product requirement list asks for.

## Not met in v1.0

| ID | Requirement | What is missing | Suggested v1.1 action |
|---|---|---|---|
| F-17 | Employees shall view available shift swap requests. | There is no employee-facing open/claimable swap list. `SwapRequestsPage` is manager-only and a swap names a specific `employeeToId`; an Employee sees only swaps where they are already the target. | Decide the semantics. For a minimal v1.0, expose the existing targeted requests read-only to Employees. For a real marketplace, make `employeeToId` optional, add an open-request query and a claim workflow; this is a contract and domain change. |
| U-01 | Responsive desktop and mobile UI. | The shift planner is a fixed `240px + 7 * 150px` grid inside `overflow: hidden`; on a phone it is clipped. There is only one breakpoint at 640 px. | Add a horizontal-scroll wrapper or a mobile card layout; test desktop and 390 px viewports with Playwright. |
| R-01 | Minimum monthly availability of 99.9%. | The delivered environment is a single-node Docker Desktop stack with mostly one replica. No SLO measurement exists. The AKS/multi-zone plan is documented but not implemented. | Implement the cloud/AKS topology with multi-zone replicas, PDBs, anti-affinity and managed databases, then measure availability. Otherwise state clearly in the report that R-01 is a v1.1/cloud target. |
| P-03 | Notifications delivered within 5 seconds. | `useNotifications` polls every 30 seconds. Backend event-to-notification latency is also not measured. | Poll at 5 seconds or add SSE/WebSocket; measure event timestamp to UI-visible timestamp. |
| S-05 | Distributed tracing across service boundaries. | No service has `micrometer-tracing`/OpenTelemetry dependencies. The OTel collector only exports to `debug`; Tempo is not running. `OTEL_EXPORTER_OTLP_ENDPOINT` is set but unused. | Add OpenTelemetry tracing dependencies, propagate `traceparent` over HTTP and RabbitMQ, export to Tempo and add a trace assertion. |
| O-04 | Automated daily database backups. | There is no active microservice backup script or CronJob. `scripts_old/backup.sh` belongs to the archived monolith. | Add Postgres/Mongo backup CronJobs with retention and a restore test, or use managed-database PITR in the cloud plan. |

## Partial in v1.0

| ID | Requirement | Gap | Suggested v1.1 action |
|---|---|---|---|
| F-03 | Role-based access control for Employees, Managers and Administrators. | Route-level roles exist, but read authorization is broad: `GET /v1/leaverequests` returns all requests to any authenticated token. | Add viewer-aware leave queries; keep Managers/Administrators all-scope and Employees own-scope. Add security tests. |
| F-07 | Administrators manage job roles. | CRUD endpoints exist in `ReferenceDataController`; there is no frontend page or route. | Add `JobRolesPage` with list/create/edit/delete and nav entry. |
| F-08 | Administrators manage work locations. | CRUD endpoints exist; there is no frontend page or route. | Add `WorkLocationsPage` with list/create/edit/delete and nav entry. |
| F-12 | Managers view shifts by department or work location. | GraphQL accepts `departmentId` and `workLocationId`; the frontend has no filter controls and never sends those arguments. | Add filter controls to `ShiftPlannerPage` and pass them through the GraphQL variables. |
| F-14 | Authorized users view leave requests. | The frontend hides other employees' requests, but the API returns all to any authenticated caller. This is a server-side privacy gap. | Restrict the query role by JWT viewer; add `LeaveQueryApiIT`/`LeaveSecurityIT` cases for own-only vs manager/admin. |
| F-18 | Identify eligible employees who can take over a shift. | AI candidate filtering is correct, but the swap picker lists all active employees; invalid choices are only rejected by `AssignmentPolicy` after submission. | Add an eligibility query for a shift or reuse the candidate rules; filter the swap picker by active, qualified, free and not-on-leave. |
| F-20 | Notify users of shift changes, leave decisions, swaps and AI suggestions. | Assignment, swap, leave, understaffed and AI events are covered. Non-cancelled `scheduling.shift.updated.v1` events do not notify assigned employees, and email is skipped for all shift updates. | Add recipients to the shift event or publish assignment-level changes; add a notification IT for a changed shift time. |
| F-21 | AI replacement suggestions when a shift becomes understaffed. | Ranking and fallback exist, but understaffed events are published only after assignment cancellation/release/delete, not when a newly created shift is understaffed. | Trigger understaffing analysis after shift creation or required-role changes; add a test. |
| F-22 | All functionality accessible through the frontend. | No job-role or work-location management pages, no department/location filters, no employee open-swap view. The settings page is a placeholder. | Complete the frontend work in F-07, F-08, F-12 and F-17; keep the report's scope statement explicit. |
| U-03 | Clear validation messages for invalid input. | Forms use HTML `required` and show one generic `alert-error`; there is no field-level error state or mapping of RFC 9457 field errors. | Add field-level validation, `aria-invalid`, and map server problem details to fields. |
| U-04 | In-app and email notifications when enabled. | In-app bell and email outbox exist, but there is no user-level notification preference and shift updates are not emailed. | Add notification preferences and include shift updates in the email policy. |
| R-03 | Automatically recover failed service instances through orchestration. | Kubernetes Deployments restart crashed pods, but almost all use `replicas: 1` and none has a liveness probe. A hung process is not restarted. | Add liveness probes, PDBs and at least two replicas for critical services. |
| R-06 | At-least-once event delivery. | Consumers retry and record `processed_event`; the outbox relay has no publisher confirms/mandatory-return handling, so end-to-end delivery is not proven. | Enable correlated publisher confirms and returns; mark outbox rows published only after confirmation; add a broker-failure test. |
| P-01 | 95% of read API requests under 300 ms. | At 50 concurrency the schedule query measured p95 198 ms; at 200 concurrency it measured p95 1,883 ms. Only the schedule read was measured. | Tune query replicas, Mongo indexes, Hikari and JVM; run 200 concurrent users and all read endpoints; publish p95. |
| P-05 | Support 200 concurrent users, verified with a load test. | A 2,000-request / 200-concurrency burst completed with 0 errors, but it used one JWT and a burst, not 200 distinct users. p95 was 1.9 s. | Add a sustained 200-user test with distinct sessions, think time and a written acceptance threshold. |
| S-04 | Structured logs for centralized monitoring. | Correlation IDs are in MDC and Promtail/Loki attach container labels, but application logs are plain text, not JSON fields. | Add a JSON Logback encoder with correlationId/traceId and parse it in Promtail; document the Loki labels. |
| A-04 | Reads stay available during a write-service outage. | The Caddy/primary path and query-role boot tests support this. The optional `kubernetes/ingress.yaml` sends leave GETs to `leave-command`, so it breaks the property if used. | Route leave GETs to `leave-query`, or route all `/api` through the Caddy `api-gateway`. |
| SE-01 | All client-service communication uses TLS 1.2 or higher. | Compose Caddy and the K8s `api-gateway` use HTTPS with Caddy's internal CA, but `kubernetes/ingress.yaml` has no TLS block and internal RabbitMQ/Postgres links are plaintext. | Add ingress TLS/cert-manager. If only browser-to-gateway is in scope, state that explicitly; otherwise add internal TLS/mTLS. |

## Measurements to quote

The running Compose stack was measured with two `scheduling-query` replicas:

| Run | Result |
|---|---|
| 2,000 requests / 50 concurrency | 550.5 req/s, 0 errors, p50 76 ms, p95 **198 ms**, p99 304 ms |
| 2,000 requests / 200 concurrency | 363.5 req/s, 0 errors, p50 283 ms, p95 **1,883 ms**, p99 2,312 ms |
| Earlier documented run, 10,000 / 50 | 1,068 req/s, 0 errors, p50 41 ms, p95 **94 ms**, p99 146 ms |
| Earlier documented run, 30,000 / 60 | 948.5 req/s, 0 errors, p95 **143 ms**, p99 227 ms |

Use these numbers as local evidence, not as a production SLO. They show that P-01 passes at 50-60 concurrency and does not pass at 200 concurrency on this machine.

## Suggested report wording

**Core course scope.** The v1.0 architecture satisfies the course requirements: seven independently deployable services, asynchronous messaging, REST and GraphQL, JWT plus OIDC, an AI workflow, CQRS, tombstones/snapshots, idempotency, commutative handlers, a compensating saga, logging/monitoring, containerization, local LLM, serverless, versioning and the required test and documentation levels.

**Honest limitation paragraph.** The larger product requirement list has 39 met, 18 partial, 6 not met and 2 not verified items. The gaps are concentrated in frontend completeness and usability, read-data authorization, notification latency, distributed tracing, production availability, backups and proof of scale. They are tracked in `docs/v1.1-backlog.md` and do not change the assessment of the course's core architecture requirements.

**Scope statement for swaps.** If the open marketplace is deferred: "v1.0 implements targeted shift swaps where an employee proposes a named colleague and a manager approves or rejects the handover. An open marketplace where employees can browse and claim available swaps is planned for v1.1."

## Do not claim

- Do not claim that all 65 product requirements are met.
- Do not claim 99.9% availability from the local single-node environment.
- Do not claim distributed tracing; only logs and metrics are implemented.
- Do not claim 200 concurrent users at the 300 ms p95 target; the current result is p95 1.9 s at 200 concurrent requests.
- Do not claim that a 1,000-employee dataset or a write-latency benchmark has been run.
- Do not claim daily database backups.
- Do not claim that the full Kubernetes application stack, including ingress and all databases, has been smoke-tested end to end.
- Do not claim that Employees can browse open swap requests.
